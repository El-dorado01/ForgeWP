# ForgeWP Edge-Case & Integrity Audit

## Purpose

This is a living document, not a bug tracker. The goal is to deliberately attack ForgeWP's assumptions — the same class of assumption that broke on hotelchecker24.com (see the "Routing & Page Links" section below for the fully-diagnosed case) — and record what we find, whether or not it gets fixed immediately. Each entry states what the framework *assumes* to be true, what happens when that assumption is violated, how bad it is, and how hard it'd be to fix.

We are not trying to enumerate every possible bug. We're trying to find every place the compiler bakes in an assumption about live WordPress state that a human editor can later invalidate without knowing they've done anything wrong — because that's the exact shape of bug that's expensive to find in production and cheap to find here.

## Methodology

- **Compile-time / pure-PHP-logic edge cases** (malformed/unusual source patterns, config edge cases, and — as it turned out to be the most efficient approach in practice — individual generated PHP functions like `forgewp_resolve_route_page_id()` and the forms validation pipeline): tested by extracting the actual function source verbatim from real compiler output and running it against small isolated PHP harnesses that stub just the specific WP/Polylang functions each one depends on (`get_pages()`, `get_permalink()`, `pll_get_post()`, etc.). This gives exact, repeatable control over each scenario — deleted post, duplicate marker, missing translation, bogus input — without needing a real WP install or database at all, and turned out faster and more precise than live-state manipulation for anything expressible as "given these function inputs/stubbed WP responses, what does this code path return." Harness scripts are currently in scratch (not committed) — worth promoting the useful ones into `packages/compiler/test/` as real regression tests, see the running "remaining work" list below.
- WP-CLI was attempted for scripted live-WP state manipulation but hangs during bootstrap in this environment (works up through DB connection, then stalls — likely a plugin phoning home) and wasn't worth further time to debug.
- Direct MySQL (`mysql.exe` bundled with Local, host `127.0.0.1:10018`, db `local`) remains the fallback for anything that genuinely requires real WP/Polylang state (taxonomy relationships, actual page hierarchies) that can't be meaningfully stubbed — not yet needed in this pass, since the isolated-harness approach covered everything attempted so far, but expected to be necessary for deeper multilingual (§4) and caching (§6) scenarios.

## Severity scale

- **Critical** — silently produces wrong output on a real page (broken link, wrong content, security-relevant), no error surfaced anywhere.
- **High** — breaks a feature entirely under a realistic scenario, but fails loudly enough that someone would notice quickly.
- **Medium** — degrades gracefully (falls back to something reasonable) but not to the *correct* thing.
- **Low** — cosmetic, or only reachable in a contrived scenario unlikely on a real client site.

## 1. Routing & Page Links — `forgewp_resolve_route_page_id()` and friends

**Status: root cause fully diagnosed and fixed (2026-07-18) on hotelchecker24. This section is the template for how every other category below should end up looking.**

### 1.1 — Page's assigned template no longer matches what the compiler expects
- **Assumption**: a route's page can always be found by matching `_wp_page_template` against the compiler-generated template filename.
- **Reality**: any editor can switch a page's template to a generic block-based one (e.g. "ForgeWP Builder") via ordinary wp-admin UI, at any time, with no warning.
- **Found**: Yes — this is what broke the Contact/Hotels/Hotelvergleiche links on hotelchecker24.
- **Severity**: Critical (silently wrong URLs, no error).
- **Fix status**: Fixed. Introduced a durable, template-independent `forgewp_route_id` post meta marker, tagged once at page-creation/discovery time, checked first with template-match as a legacy fallback.

### 1.2 — Polylang implicitly scopes "search all languages" queries to the current language
- **Assumption**: `get_pages()`/`get_posts()` without an explicit `lang` argument searches across all languages.
- **Reality**: Polylang silently restricts these queries to the current page's language unless `'lang' => ''` is explicitly passed.
- **Found**: Yes — this is why the `forgewp_route_id` fix didn't work on first deploy even after the marker was correctly set.
- **Severity**: Critical (silent, no error, only reachable when deliberately cross-language searching — meaning any *future* code that does an unfiltered lookup is at risk of the same bug).
- **Fix status**: Fixed in `forgewp_resolve_route_page_id()`. **Open question**: are there other `get_pages()`/`get_posts()`/`WP_Query` call sites in the generated PHP that intend a cross-language search but don't pass `'lang' => ''`? Worth a full grep audit of the compiler for every `get_pages(`/`get_posts(` call site as a follow-up task (§7 below).

### 1.3 — Compiler's slug-guessing heuristic diverges from a human-created page's real slug
- **Assumption**: when a route isn't findable, `pagesToAutoCreate`'s fallback slug guess (strip `-page` from the template slug) is a safe default.
- **Reality**: if a human already created the real page independently (common — e.g. via an agency setting up initial content before the compiler ever auto-created anything), the real slug can differ arbitrarily (`contact` vs. guessed `kontakt`).
- **Found**: Yes — root cause of why `forgewp_auto_create_pages_and_menus()`'s own page-discovery (`get_page_by_path($p['slug'])`) never found the anchor to tag it automatically.
- **Severity**: High (breaks auto-tagging silently; the *link resolution* itself still works once `forgewp_route_id` is manually or automatically set some other way, but auto-discovery on a fresh but human-touched install won't self-heal).
- **Fix status**: Not fixed — worked around manually (temporary snippet) for this one site. **Needs a real design decision**: should the compiler stop guessing entirely and require an explicit slug in `wp.config.ts` per route? Or should `forgewp_auto_create_pages_and_menus()` try a secondary discovery pass (e.g. by template match, in any language) before giving up on tagging? Candidate for §7.

### 1.4 — Un-published / draft translation pages 404 even when everything else resolves correctly
- **Assumption**: n/a — this isn't a ForgeWP bug at all, but worth recording because it looked exactly like one during debugging.
- **Reality**: a translation page left in Draft status (e.g. forgotten during initial site setup) 404s for anonymous visitors regardless of any link-resolution logic being correct.
- **Found**: Yes (the English Contact page, post 33).
- **Severity**: N/A (content/editorial issue, not a framework issue) — but **recommendation**: the compiler could add a wp-admin notice/dashboard widget warning when a page tagged with `forgewp_route_id` (or matched by legacy template) is not in `publish` status, since this is indistinguishable from a real bug without server access.

### 1.5 — Tested via isolated harness (stubbed WP/Polylang functions, not live WP — see methodology)

Rather than manipulating real WP/Polylang state via SQL for each scenario, `forgewp_resolve_route_page_id()` was extracted verbatim and run against a small PHP test harness stubbing `get_pages()`, `get_permalink()`, `pll_current_language()`, `pll_get_post()` — giving exact, repeatable control over each edge case without needing a real database. Script kept at `edge-case-audit-harness/test-route-resolution.php` conceptually (currently in scratch, not committed — candidate for a real `packages/compiler/test/` addition, see §7.4-style follow-up).

- **Translation target itself deleted/invalid** (anchor found, `pll_get_post()` still returns an ID, but that post no longer exists): **Real gap.** `forgewp_resolve_route_page_id()` returns the stale ID; every call site does `$target_id ? get_permalink($target_id) : $fallback`, and since the stale ID is still truthy, `get_permalink()` is called on a nonexistent post, returns `false`, and `esc_url(false)` silently produces an **empty string** — not the developer's fallback. A deleted page (without its Polylang translation link being cleaned up first) turns into a dead, empty `href=""` rather than degrading to the fallback. **Severity: Medium** (requires an unusual state — a translation target deleted without also clearing the translation group — but produces a worse-than-fallback result: `href=""` rather than a working default link).
- **Duplicate `forgewp_route_id` on two pages** (e.g. a page duplicated in wp-admin, or the manual-tagging snippet run against the wrong post twice): **Real gap.** Nothing prevents this, and `get_pages(..., 'number' => 1)` returns whichever row it returns first with no defined tiebreak (dependent on `wp_postmeta` insertion order, not something the framework validates or warns about). Which of the two pages "wins" is effectively undefined behavior. **Severity: Medium** (silent, but only reachable via an editing mistake, and the *outcome* — landing on *some* real page rather than a broken one — is less bad than other findings here).
- **Anchor tagged, but its Polylang translation link removed/never created** (a very ordinary, plausible state — e.g. a page hasn't been translated into the second language yet): **Real gap, and the most concerning of this batch.** `pll_get_post()` returns `0`, so resolution silently falls back to the **anchor's own page — in the anchor's own language** — rather than the developer-supplied fallback. Concretely: on an English page, if the German anchor has no English translation yet, the "Contact" button resolves to a real, working German URL instead of the intended fallback. This is worse than a dead link because it looks completely legitimate (a real, clickable, correctly-formed URL) and wouldn't be caught by casual QA the way a 404 or empty href would — someone would have to actually click it and notice they landed in the wrong language. **Severity: High.**
- **Polylang inactive entirely** (`pll_get_post`/`pll_current_language` undefined): covered by existing `function_exists()` guards in the source; verified by code review rather than the runtime harness (PHP can't undefine an already-declared function mid-script to simulate this dynamically). Looks correct as written.
- **Anchor page's own language reassigned after tagging** (e.g. the German anchor gets reassigned to English in Polylang): **traced through, not a new bug — collapses into the finding already above.** Polylang detaches a page from its translation group when its language is changed (documented Polylang behavior, not ForgeWP's to fix), so `pll_get_post($anchor_id, $current_lang)` on the now-reassigned anchor returns `0` exactly as in the "translation link removed" case already documented two bullets up. Same mechanism, same fallback-to-anchor's-own-page-in-wrong-language outcome, same severity — not counted as a separate finding, just confirmation the existing High-severity finding covers this trigger too.
- **Not yet tested**: Multisite — untested, unknown if any of this logic is multisite-aware at all.

## 2. Forms system (`submitWpForm` / `<WpFormFields>` / `forms` config)

### 2.1 — Submitting a bogus `lang` value bypasses required-field validation for client-owned fields (confirmed via runtime test, not speculative)

- **Mechanism**: `forgewp_handle_form_*()` (the REST submission handler) resolves which client-owned field definitions apply by reading `$submitted_lang` directly from the submitter's own POST data (`isset($params['lang']) ? sanitize_key($params['lang']) : null`), then calls `forgewp_forms_get_client_fields($form_name, $seed_fields, $submitted_lang)`. If the resolved language doesn't match any key in the multilingual seed array, that function's final line returns an **empty array** (`isset($seed[$resolved_lang]) ? $seed[$resolved_lang] : array()`). `$field_defs` then only contains developer-baked fields (`$dev_fields`) — any client-added field (added later by the client through the forms admin UI, entirely separate from the compiled config) is simply absent, and `forgewp_forms_validate_and_sanitize()` only ever iterates over `$field_defs`, so a missing client-owned field is never checked, never validated, and never captured — with no error returned to the submitter.
- **Verified with a runtime test** (isolated harness, copying the real functions verbatim): a multilingual form with a `required` client-owned "Phone Number" field, submitted with `lang=en` and no phone, is correctly rejected (`"phone": "This field is required."`). The identical submission with `lang=zz-not-a-real-locale` is **accepted**, phone silently absent from the captured values, zero errors.
- **Impact**: this only affects **client-owned fields** (added post-launch via the forms admin UI) — developer-baked fields in `$dev_fields` don't depend on language resolution at all and aren't affected. But for any site using client-owned required fields (e.g. a client adds a "required: phone number" field to weed out low-quality leads), this is a trivial, no-special-access way to submit the form while skipping that requirement entirely — reachable by anyone who inspects the request payload and changes one parameter, not a sophisticated attack.
- **Severity**: High (silent validation bypass, no error surfaced, trivially reachable, undermines a guarantee — "required" — that a non-technical client configured through the admin UI and would reasonably expect to be enforced).
- **Fix direction**: `forgewp_forms_get_client_fields()`'s fallback for an unrecognized language shouldn't be an empty array — it should fall back to the seed's default/primary locale (mirroring how `forgewp_forms_resolve_lang()` itself falls back through Polylang → default language → site locale rather than ever silently returning nothing), so an unrecognized `lang` degrades to "validate against a real locale's fields" rather than "validate against no client fields at all."

### 2.2 — Traced through this pass (code-level, not live-WP)

- **Multiple forms on the same page**: **cleared.** `submitWpForm(name, data)` scopes every submission by an explicit form `name` in the REST URL (`/forms/${name}/submit`), and each call site owns its own `FormData`/state independently (ordinary React component-instance behavior) — there's no shared global keyed by form name that two instances could collide on. The one genuinely shared piece of client state is the honeypot input's `name="_forgewp_hp"` (`WpFormFields.tsx:64-71`), which is a plain `name` attribute duplicated across however many `<form>`s render it — legal HTML (only `document.forms[name]` lookups would care, and nothing here does one), and each browser-native form submission only serializes its own descendant inputs regardless. The time-trap baseline (`forgeWpFormsLoadedAt`, `hooks.ts:219`) is a module-load timestamp shared across all forms on the page — correct by design, since "time since page load" should be the same reference point for every form on that page, not per-instance.
- **A form field renamed/removed in `wp.config.ts` after real submissions already exist**: **cleared, safer than expected.** `forgewp_render_submission_meta_box()` (`forms.js:538-554`) builds its detail view straight from `get_post_meta($post->ID)` filtered to keys with a `field_` prefix — i.e. from what was *actually stored at submission time* — not from the current `$field_defs`. A field renamed or deleted from config later doesn't touch already-stored `forgewp_submission` posts at all; old submissions keep displaying their original data under their original (now-orphaned) label, indefinitely. The list-view "Form" column and its filter dropdown key off `_form_name`, not individual field names, so they're unaffected either way.
- **Client adds/removes fields via the forms admin UI interacting with `forgewp_route_id`-style page-template drift**: **cleared, not applicable.** The forms field-editor (`forgewp_render_forms_admin_page()` / `forgewp_forms_admin_save_handler()`, `forms.js:892+`) is a `wp-admin` submenu page, not a `forgewp_route_id`-tagged frontend route — it isn't reached through the page/template resolution system §1 is about at all, so there's no shared failure mode to interact with.
- **Client-added field name colliding with a dev-owned field**: found a real (Low-severity) gap while tracing this. The runtime admin save handler does defend against it — `if (in_array($name, $used_names, true) || in_array($name, $dev_field_names, true)) { continue; }` (`forms.js:848`) — but it fails by **silently dropping** the colliding field from what gets saved, with no error surfaced back to the admin UI explaining why the field they just added didn't appear. Safe (no data corruption, no dev-field overwrite), but confusing: a site owner adding a field named e.g. `message` (colliding with a common dev-owned field) would just see it vanish on save with no explanation. **Fix direction**: return a specific error from the AJAX handler when a submitted name collides, instead of silently filtering it out.
- **Shortcode-escape-hatch mode (third-party plugin like Contact Form 7) alongside native forms**: confirmed the compiler is aware of the distinction (`shortcodeModeNames` is checked when validating `<WpFormFields>` usage, `forms.js:89`) but this is purely a compile-time lint concern (warns if `<WpFormFields>` targets a shortcode-mode form). Whether a shortcode-mode form and native forms collide in the admin submissions list wasn't independently traced — shortcode-mode forms presumably don't create `forgewp_submission` posts at all (they're handed off entirely to the third-party plugin), which would mean no collision by construction, but this is inferred from the naming, not directly verified against the shortcode-mode code path. Still open.
- **`mailTo` delivery when `wp_mail()` isn't configured**: unchanged from the prior pass — confirmed by inspection that a failed `wp_mail()` still reports success to the submitter as long as `storeSubmissions` is enabled and the DB write succeeded (`if (!$mail_sent && !$stored)` only fails the whole request when *both* fail). Reasonable tradeoff, but worth flagging to a client explicitly rather than them discovering it the day they realize a submission sitting in the database never reached their inbox.

## 3. Auth (registration, login, email verification)

### 3.1 — Custom registration fields: the plumbing exists on the client and is a dead end on the server (confirmed, not speculative)

This directly answers the question you raised earlier ("should clients be able to manage custom registration fields") with hard evidence, and the answer is: **that question is premature — the developer-level version doesn't actually work end-to-end yet.**

- **Client-side hook** (`packages/auth/src/hooks.ts:416`): `useWpAuth().register(username, email, password, metadata?: Record<string, any>)` — takes a fourth `metadata` argument, and when it calls the real (non-dev-mock) endpoint, it genuinely sends it: `body: JSON.stringify({ username, email, password, metadata })` (line 468). The wire protocol was clearly *designed* to carry arbitrary custom fields.
- **Canonical signup form template** (`packages/compiler/templates/auth/components/signup-form-wrapper.tsx`): only collects username/email/password/confirm-password, and calls `register(trimmedUsername, trimmedEmail, trimmedPassword)` — **never passes a fourth argument at all.** No UI exists in the shipped template for a developer to add a custom field without rewriting this file from scratch.
- **Server-side handler** (`forgewp_rest_signup()` in `packages/compiler/lib/functions/rest-endpoints.js:639`): reads exactly `email`, `username`, `password`, `displayName` from `$request->get_json_params()`. **Zero references to `metadata` anywhere in this file** (confirmed via grep) — if a developer *did* write a custom form and passed `metadata`, it would be silently dropped on arrival, never persisted as user meta, with no error anywhere.
- **Severity**: High, as a product-completeness gap rather than a "wrong behavior" bug — this isn't corrupting anything, it's a half-built feature: client-side signature suggests support, template doesn't use it, server discards it if you try anyway.
- **Recommendation**: this needs the same design pattern already proven for forms (`submitWpForm()` + `<WpFormFields>` + a declarative `forms` config key — see `forgewp_forms_spec.md` / Principle 11's "no new component vocabulary" rule) rather than a bespoke solution: likely a declarative `auth.registrationFields` config key in `wp.config.ts`, server-side generation of the corresponding `update_user_meta()` calls in `forgewp_rest_signup()`, and the signup template reading that same config to render the extra fields — mirroring how forms already solved "let a client add/remove fields without a new component vocabulary."

### 3.2 — Traced through this pass (code-level, not live-WP)

- **Reserved username collisions, case-sensitivity**: **cleared, verified both sides of the boundary.** `reservedUsernamesPhp` is built at compile time by `reservedUsernames.map(u => u.toLowerCase()...)` (`functions/index.js:52`), and the runtime check compares `strtolower($username)` against that array with a strict `in_array(..., true)` (`rest-endpoints.js:673-674`). Both sides are lowercased consistently before comparison — `Admin`, `ADMIN`, and `admin` are all correctly caught. No gap.
- **Email verification page (`verify-email-page`) suffering the exact §1.1–1.3 template/routing drift**: **confirmed, not a separate code path.** `rest-endpoints.js:1916` calls `forgewp_resolve_route_page_id('verify-email-page')` — the identical shared function §1 is about. This means the verify-email link inherits *every* finding already documented in §1.5 (missing-translation → wrong-language fallback, deleted-translation-target → dead empty href, duplicate-marker → undefined tiebreak) automatically, with no additional verification needed — fixing §1's function fixes this route too, and any regression there breaks this route identically.
- **Auto-login-after-signup interacting with email-verification-required**: **cleared, confirmed by reading the actual runtime code** (not just inference this time): `rest-endpoints.js:710-724` — `$auto_login = get_option(...) === '1'; if ($auto_login && ! $verification_enabled) { ... wp_signon ... }`. Auto-login is only ever attempted when verification is *disabled*; when verification is required, the function falls through to the plain "Registration successful, please verify your email" response with no session created. Correct as written.

## 4. Multilingual / Polylang integration generally

### 4.1 — Polylang deactivation safety: checked, no issue found
Grepped every `pll_*()` function call site across the compiler (`pll_current_language`, `pll_default_language`, `pll_the_languages`, `pll_home_url`, `pll_register_string`, `pll_get_post`, `pll__`) and manually verified each one's surrounding context. **All of them are properly wrapped in `function_exists()` guards** with sensible fallbacks (`get_locale()`, `home_url('/')`, or simply skipping the Polylang-specific behavior). No fatal-error risk found if Polylang is deactivated after a site was built with it active. This is a genuine "cleared" item, not just an assumption.

### 4.2 — More-than-two-languages: no framework-level hardcoding found, but found an unrelated, real hardcode elsewhere
Went looking for a 2-language (DE/EN) assumption baked into the framework itself, since hotelchecker24's UI (the binary DE/EN toggle switch in `Navbar.tsx`) *looks* hardcoded to two languages. **That turned out to be a project-level choice, not a framework limitation** — the framework does provide a genuinely N-language-capable primitive (the `<forgewp-language-switcher>` markup-processor output loops over `pll_the_languages()` dynamically and renders however many languages Polylang has configured); hotelchecker24 simply chose to hand-roll a simpler binary toggle instead of using it.

While checking this, found a real, separate, framework-level hardcode: `generate-theme.js:936-943`, the `useWpLanguage()` **block-editor-preview stub** (used only inside wp-admin's Gutenberg block editor canvas when a developer is editing a block that calls `useWpLanguage()` — confirmed via an explicit comment a few lines above: "Keep this list in sync with `wordpress.tsx`'s exported useWp\* hooks... execute in the block editor's preview without throwing"), is hardcoded to `{ currentLanguage: 'de', languages: ['de', 'en'] }` for every ForgeWP project, regardless of that project's actual configured `i18n.locales`. **Impact is limited to the wp-admin block editor preview UX** — never reaches real visitors or the compiled frontend — so for any non-DE/EN project, a developer editing a language-aware block in wp-admin would see a wrong/misleading preview (stuck showing "de" as current, only two phantom "de"/"en" options) rather than their site's real languages. **Severity: Low** (cosmetic, editor-only, doesn't affect anything a site visitor sees) but **easy, concrete fix**: this stub is generated inside a function that already has `config` in scope elsewhere in the same file — it should read `config.i18n.locales` / `config.i18n.defaultLocale` instead of the two literal strings.

### 4.3 — Traced through this pass (code-level, not live-WP)

- **Language switcher behavior when the current page has no translation in the target language**: **cleared — and notably safer than §1's route-marker mechanism.** The `<forgewp-language-switcher>` primitive calls `pll_the_languages(array('raw' => 1))` (`markup-processor.js:250`) with no `hide_if_empty` override, so it inherits Polylang's own default (`hide_if_empty` defaults to `1` in Polylang core). This means a language with no translation of the current page is simply **omitted from the rendered switcher nav entirely**, rather than linking anywhere. That's the opposite failure mode from §1.5's `forgewp_resolve_route_page_id()` finding (which silently falls back to a real-but-wrong-language URL) — here, the visitor never sees a link they could click into the wrong language in the first place. Worth noting as a real asymmetry in the framework: the *route-marker* resolution path (used for Contact/Hotels-style fixed routes) and the *on-page switcher* path (used for post/page translations directly) handle the identical "no translation exists" scenario completely differently, one silently wrong, one silently (and correctly) hiding the option. Not a bug in the switcher — worth calling out as a reason to consider bringing §1's resolution logic in line with this safer default (explicit "omit/fallback" behavior) rather than "resolve to the anchor's own language."
- **`pll_default_language()` changed after launch**: unchanged from the prior pass — every read site calls the function fresh, nothing cached at compile time, looks safe by inspection, not independently runtime-verified (would need live Polylang state to actually flip the default language and observe behavior, not something the isolated-harness approach can simulate meaningfully here).
- **Not yet tested**: Multisite — completely untested, unknown if any of this logic is multisite-aware at all.

## 5. SEO plugin interoperability

### 5.1 — The exact bug class caught in project-level `og-fallback.php` also exists at the framework level, currently live, unfixed

This session's earlier work (see conversation history) caught and fixed a self-authored bug in hotelchecker24's own `src/server/og-fallback.php`: it printed duplicate meta tags because it checked SEO-plugin-active status with logic that could drift out of sync with `header.php`'s own check. That was fixed for that one project-specific file. **The same duplicated-detection pattern exists in the compiler itself, in three separate places, and two of the three are already out of sync with the third:**

- `php-builders.js:220-224` (the canonical check, gates whether `header.php` prints its own static `<head>` content): checks `WPSEO_VERSION`, `RankMath`, `All_in_One_SEO_Pack`, `AIOSEO_VERSION`, **and `SEOPress\Services\Title`** — 5 conditions.
- `functions/routing.js:394` (gates `forgewp_custom_document_title()`, the `pre_get_document_title` filter that overrides the page `<title>`): checks the same 4 plugins, **missing SEOPress**.
- `functions/theme-setup.js:133` (gates `forgewp_register_segmented_xml_sitemaps()`): checks the same 4 plugins, **missing SEOPress**.

**Concrete impact for any site using SEOPress specifically** (untested live, but directly traceable from the code): `header.php` correctly detects SEOPress and suppresses its own head content — but `forgewp_custom_document_title()` doesn't know SEOPress is active, so it still tries to override the page's `<title>` by extracting one from ForgeWP's own static head-target file, at filter priority 999 (very late — likely wins over SEOPress's own title filter), silently undermining whatever SEO title the site owner configured through SEOPress. Separately, `forgewp_register_segmented_xml_sitemaps()` also doesn't know SEOPress is active, so it registers its own sitemap post-type/taxonomy filters *in addition to* SEOPress's, risking duplicate or conflicting sitemap entries.

- **Severity**: High (silent, no error, actively fights a site owner's real SEO configuration — the exact opposite of Principle 4, "yield gracefully to standard WordPress SEO plugins").
- **Fix direction**: extract the 5-condition check from `php-builders.js` into one shared PHP function (e.g. `forgewp_seo_plugin_active()`) generated once, and have all three (and any future) call sites use it — exactly the kind of single-source-of-truth fix already applied to `forgewp_resolve_route_page_id()` in §1.1, and the same category of fix already manually applied to hotelchecker24's own `og-fallback.php`. This is a clear, mechanical, low-risk fix once prioritized.

### 5.2 — Traced through this pass (code-level, not live-WP)

- **No SEO plugin at all, at the framework-level `php-builders.js` head-injection path specifically**: **cleared.** Read `buildHeaderPhp()` (`php-builders.js:206-254`) directly: when `$seo_plugin_active` is false, `header.php` prints ForgeWP's own head content from `forgewp_resolve_head_target()`, explicitly stripping only the `<title>` tag via regex (`preg_replace('/<title>.*?<\/title>/is', '', $content)`) and deferring the title itself to `wp_head()`'s standard title-tag support plus `forgewp_custom_document_title()`'s `pre_get_document_title` filter. Division of responsibility is clean and doesn't duplicate — confirms the "no plugin" path is correct by construction at the framework level, not just for hotelchecker24's project-specific fallback file.
- **Yoast and RankMath schema-graph integration specifically**: read the actual generated code (`functions/index.js:61-100`) rather than just noting it exists. Both integrations work the same way: parse `forgewp_resolve_head_target()`'s rendered output for `<script type="application/ld+json">` blocks and merge the decoded JSON into the plugin's own graph (`wpseo_schema_graph` filter for Yoast, `rank_math/json_ld` for RankMath). This is structurally sound and **can't double-print**, because it's gated behind the same "SEO plugin active" condition family that already makes `header.php` suppress its own raw output — the schema-graph filter is the *only* place that content reaches the page when either plugin is active. **Found a real, previously-undocumented Low-severity gap while tracing this, though**: the schema-graph merge is opt-in via `config.seo.plugins.yoast` / `config.seo.plugins.rankMath` in `wp.config.ts`, but `header.php`'s suppression check is presence-based (`defined('WPSEO_VERSION')`, etc.) — the two aren't the same flag. If a developer has Yoast actually installed but never set `config.seo.plugins.yoast = true`, `header.php` still correctly suppresses ForgeWP's own output (no duplication, safe), but the schema-graph merge never registers, so ForgeWP's enqueued schema silently never reaches the page at all — not a duplication bug, but a silent, easy-to-miss "your schema just isn't there" gap whenever the config flag and the actually-installed plugin drift out of sync. **Fix direction**: detect the plugin presence-based (like `header.php` already does) and enable schema-graph merging automatically, rather than requiring a second, independent manual opt-in flag that has no relationship enforced with the first.
- **Two SEO plugins active simultaneously**: traced through — `$seo_plugin_active` is a single OR'd boolean, so ForgeWP correctly treats "any known plugin active" as "yield entirely," regardless of how many are active. Any duplication *between* the two plugins' own outputs is a WordPress ecosystem multi-plugin conflict outside ForgeWP's control or responsibility — not a framework bug, out of scope for this audit.
- **Schema/JSON-LD conflicts between ForgeWP's own schema generation and the SEO plugin's**: covered by the Yoast/RankMath bullet above — no conflict by construction when the config flag is set correctly, silent gap (not conflict) when it isn't.

## 6. Caching & deployment interactions

### 6.1 — Correction to this session's own work: `'cache' => false` on `get_pages()` is a complete no-op in modern WordPress

This is worth flagging prominently because it corrects an assumption baked into code written *earlier in this same session* (and present in the pre-existing codebase before today, with detailed comments explaining why it was believed necessary).

- **Checked directly against WP core** (`wp-includes/post.php`, the actual version running on the local site): `get_pages()`'s `$defaults` array does not include a `'cache'` key at all, and grepping the entire function body for `'cache'`, `cache_results`, `wp_cache_get`, `wp_cache_set` returns **zero matches**. Since WP 6.3.0, `get_pages()` builds a `$query_args` array, runs it through an `apply_filters('get_pages_query_args', ...)` filter (almost certainly what Polylang hooks to inject the implicit language restriction found in §1.2), and hands off entirely to `new WP_Query()`. There is no code path anywhere that reads a `'cache'` argument — passing it is silently accepted (unrecognized `WP_Query` args are just ignored) and does **nothing at all**.
- **Where this matters**: the compiled output currently carries `'cache' => false` in at least 3 places in `forgewp_resolve_route_page_id()` alone (added earlier this session, believing it was needed), and the pattern is copied throughout the pre-existing codebase with a comment reading "get_pages()'s own cache key doesn't account for the 'lang' arg... without this, the first language to run this query gets cached and reused for every other language." **That explanation describes behavior this WP version's `get_pages()` doesn't have** — there's no such internal cache to disable. The bug that comment was originally written to explain was real (we hit it live today), but the actual, confirmed fix was the explicit `'lang' => ''` override (§1.2) working around Polylang's `get_pages_query_args` filter — not the `'cache' => false` parameter, which never did anything.
- **Is it harmful?** No — a silently-ignored, harmless extra array key. Not a correctness bug. But it's worth clearing up because: (a) it's misleading to future maintainers who'll trust the confident-sounding comment explaining a mechanism that doesn't exist, and (b) worth checking whether the *original* motivation for adding it (some observed caching-looking symptom, on some WP version, at some point) has a different, real explanation that's now being masked by an incorrect one — i.e. is there possibly a genuinely different caching issue this was cargo-culted in response to, that's still unexplained?
- **Severity**: Low (no functional harm), but flagged because of what it implies about verifying inherited assumptions rather than trusting explanatory comments at face value — the same instinct this whole audit exercise is built on.
- **Recommendation**: strip the dead `'cache' => false` args and their now-inaccurate comments across the codebase (cosmetic cleanup, not urgent), and specifically double check this against whatever minimum-supported WP version ForgeWP targets — if older WP versions' `get_pages()` genuinely did have its own cache (plausible; this may be exactly why the pattern exists), the parameter could be a correct, meaningful guard on *those* versions and only inert on this one, which would change the recommendation from "remove" to "document the version dependency."

### 6.2 — Traced through this pass (code-level, not live-WP)

- **PHP-level static caching in `forgewp_gettext_translation_bridge`**: **real, confirmed staleness risk, worth documenting prominently.** Read the actual code (`functions/routing.js:443-467`): `static $translations = null;` caches the fully-parsed contents of `translations.json` the first time the filter runs, and never re-reads the file again for the rest of that PHP process's lifetime — only the *language* (`pll_current_language()`) is re-resolved fresh on every call, not the translation data itself. This matters because PHP `static` function-local variables are a well-known PHP-FPM gotcha: they persist across every HTTP request handled by the same worker process, not just within one request — resetting only when that specific worker is recycled (`pm.max_requests`) or the FPM pool is restarted. **Concrete impact**: after redeploying a theme with an updated `translations.json` (e.g. a client fixes a mistranslated string through whatever workflow edits it), visitors routed to a worker that already served at least one request since the last restart keep seeing the **old** translation, while visitors routed to a freshly-recycled worker see the new one — simultaneously, on the same site, with no error anywhere. This is exactly the shape of "looks stale for no visible reason" trap flagged as a process cost in §8, now with a confirmed root cause. **Severity: Medium** (self-heals eventually as workers recycle naturally, doesn't corrupt anything, but can look like a flaky/broken deploy for however long the pool takes to fully cycle). **Fix direction**: either drop the `static` caching (accept the cost of re-parsing a small JSON file every request) or key the cache on the file's mtime/hash so a changed file invalidates it within the same worker instead of relying on process recycling.
- **Object cache persistence (Redis/Memcached) interacting with `WP_Query`'s `cache_results`**: reframed, not fully closed. §6.1 already established `get_pages()` delegates entirely to `WP_Query`, whose own `cache_results` defaults to `true` — so on a host with a persistent object cache backend configured, `forgewp_resolve_route_page_id()`'s underlying queries genuinely are cacheable at that layer (unlike the no-op `'cache' => false` argument). In the *normal* case this is self-healing: WordPress core clears the relevant cache groups automatically on post/meta writes made through its own APIs (`update_post_meta()`, Polylang's own save hooks, etc.), so ordinary wp-admin edits stay consistent. **The real risk window is narrower than "any object cache is dangerous"**: it's specifically edits that bypass WordPress's own save hooks — most notably, a **direct SQL `UPDATE` against `wp_postmeta`**, which is a pattern this very audit considered using as a live-testing shortcut earlier in the session. Worth documenting explicitly: on a host with persistent object caching, direct-SQL edits to `forgewp_route_id` or Polylang translation links could serve stale routing data until the relevant cache key expires or is manually flushed — a trap for whoever debugs a future site this way, including future instances of this same audit process.
- **Not yet tested / needs a team decision, not more investigation**: what is the *supported* deployment path for updating a live site (this session ended up improvising a full theme-zip reupload via Appearance → Themes → Add New — is that the intended production workflow, or should there be something more incremental)? Opcache invalidation on theme-file replacement across common hosts is in the same bucket — plausible, host-dependent, and not something resolvable by reading the compiler's own source since it's about the hosting environment, not ForgeWP's code.

- **Re-verified 2026-07-18**: **Fixed.** Confirmed against the actual current source (`HotelListicles.tsx`'s `{listiclesLoading ? (...) : matchingListicles.length > 0 ? (...) : (...)}`) and its freshly compiled `blocks/hotel-listicles/render.php` — all three branches compile to correct, cleanly nested `if/else` with no leaked text. No longer an issue.

### 7.2 — `JSON.parse()` mistranslation (from the same prior investigation)
- **Claimed bug**: `JSON.parse(x)` compiled to `($JSON ?? null).''` instead of `json_decode($x, true)`.
- **Re-verified 2026-07-18**: **Fixed.** `translateJsonParse()` now exists in `php-transpiler.js` and runs before `neutralizeUnknownJsCalls()` in `translateJsExpressionToPhp()`; confirmed against the same `HotelListicles.tsx:50` (`const parsed = JSON.parse(related)`) the original bug was reported against — compiles correctly to `$parsed = json_decode(($related ?? null), true);`. No longer an issue.

### 7.3 — NEW, currently live: JS template literals (backtick strings with `${}` interpolation) are not recognized at all
- **Found while re-verifying 7.1/7.2**, in the exact same file/block, one line below the JSON.parse call.
- **Source** (`HotelListicles.tsx:80`): `href={l.permalink || \`/hotelvergleich/${l.id}\`}` — a template-literal fallback URL.
- **Compiled output** (`blocks/hotel-listicles/render.php:30`): `$l['permalink'] ?: \`/($hotelvergleich ?? null)/${$l.($id ?? null)}\``
- **What's actually happening**: the general property-access/bare-identifier rewriting pass runs across the raw template-literal text with no special-casing for backtick strings or `${...}` interpolation — it mangles the literal text portions and the interpolated expression alike, and never converts the backtick delimiters into PHP string concatenation.
- **Why this is bad, specifically**: PHP backticks are the shell-exec operator, not a string literal. `php -l` reports **no syntax error** — this is syntactically valid PHP that does something completely different from what anyone intended (attempts to shell-exec a garbage string, almost certainly yielding null/empty). Zero visible errors anywhere; the affected link just silently goes dead whenever the fallback path is actually exercised (any hotel-listicle entry without a `permalink` field, in this specific widget).
- **Severity**: Critical (silent, no error, and worse than a typical "leaks as text" bug because it's syntactically valid PHP doing something actively wrong rather than obviously broken output).
- **Scope, fully verified**: a source-level grep for this pattern (backtick template literal with `${...}` inline in a JSX expression) hits **18 files** in hotelchecker24, but that number is the wrong way to measure it — some components (e.g. `FeaturedHotelsGrid.tsx`, confirmed below) hydrate from a completely empty server-rendered boundary, so their JS never touches PHP at all and can't be affected no matter what it contains. The reliable check is the **compiled output**, not the source. Grepping every generated `.php` file in the exported theme for a literal backtick character (which should never legitimately appear in correct PHP output) found the true, complete list directly:
  - `blocks/hotel-listicles/render.php:30` — the originally-found hit (`href` fallback URL). **Real.**
  - `blocks/hotels-workspace/render.php:78,108` — a conditional `class="..."` attribute (active/inactive filter-pill styling), same root cause. **Real** — and arguably worse than the href case, since `esc_attr()` wraps a shell-exec'd result here, meaning the affected filter buttons silently lose their active-state styling entirely, not just get a dead link.
  - `blocks/listicles-workspace/render.php:46-50` — same shape, another conditional filter-pill `class` attribute. **Real.**
  - `functions.php` (2 backtick matches) — checked and cleared: these are literal backtick characters sitting inside a large embedded JSON block-registry blob (escaped JS source code stored as string *data*, e.g. a block's "example" field), never interpreted as PHP. **False positive.**
  - `blocks/featured-hotels/render.php` — no backtick present at all; confirms the earlier finding that this component's loop hydrates from an empty boundary and never reaches PHP. **Not affected**, consistent with source-level prediction.
  - **Conclusion**: 3 confirmed real, live instances across 2 components (`hotel-listicles`, and both workspace filter-pill blocks), not just 1. Grepping compiled PHP output for a literal backtick character is a fast, reliable, zero-false-negative way to find every live instance of this specific bug class in any ForgeWP export — recommend running this same one-line grep against any other theme/site before considering it clear, rather than re-deriving from source each time.
- **Fix status (2026-07-19): Fixed, in two separate places — and the fix process itself surfaced a fourth, previously-undocumented live instance.**
  - Added `translateTemplateLiteral()` to `php-transpiler.js`, wired in as the very first step of `translateJsExpressionToPhp()` (before `translateJsonParse()`), converting `` `text${expr}moretext` `` into `'text' . (expr) . 'moretext'` — the interpolated `expr` is left as raw JS text so the rest of the existing pipeline (dot-notation rewrite, bare-identifier-to-`$var`, ternary parenthesization) still translates it exactly as it would any other part of the expression. Verified in isolation against the three documented cases plus edge cases (nested ternary inside `${}`, multiple interpolations, escaped quotes in the literal text) — all produce valid, correctly-precedenced PHP.
  - **Rebuilding hotelchecker24 with the fix and re-grepping the compiled output for backticks (the exact verification method this section recommends) surfaced a fourth, separate live instance that source-level reading had missed**: the static "Alle Länder" / "Alle Kategorien" filter buttons in `HotelsWorkspace.tsx` (lines 148 and 177 — the *unmapped*, single-button case, as opposed to the `.map()`-generated per-option buttons at lines 156/185, which the `php-transpiler.js` fix above already covers) compiled to a stray `$` sitting directly in front of a `<?php if (...): ?>` block — the leftover `$` from an unconsumed `${`. Root cause: `blocks/index.js` has its **own separate** `class={\`...\`}` → PHP handler, entirely distinct from `php-transpiler.js`'s pipeline, but it runs **after** `transpileConditionals`/`transpileTernaries` — and those two passes scan for bare `{...}` JSX expression containers with no awareness that a `${...}` inside a backtick is not one. `transpileTernaries` found the ternary sitting inside `${!country ? 'a' : 'b'}`, transpiled it in place as if it were a real top-level JSX ternary, and left the enclosing backtick/`$` behind as broken literal text — a second, independent occurrence of the exact same underlying defect class (a backtick-unaware pass running before backtick syntax is resolved), just via a different code path than the one originally found.
  - Fixed by adding a new, earlier pass in `blocks/index.js` — before `transpileLoops`/`transpileConditionals`/`transpileTernaries` — that resolves every `attr={\`...\`}` template literal (not just `class`/`className`) into a plain PHP-interpolated string first, using the same `translateJsExpressionToPhp()` (and therefore the same new `translateTemplateLiteral()`) for each `${...}` interpolation.
  - **Verified against real compiled output, not just the isolated harness**: re-ran `forgewp export` on hotelchecker24 and confirmed (a) all 3 originally-documented instances plus the newly-found 4th instance now compile to valid PHP string concatenation/inline `esc_attr()` calls with zero backticks, (b) `php -l` reports no syntax errors on every generated `render.php` in the export, not just the previously-broken ones, (c) a full-theme grep for a literal backtick character now returns only the two already-known, already-cleared false positives in `functions.php` (a JSON data blob and a doc-comment), confirming no new occurrences were missed and no regression was introduced elsewhere in the theme.
  - **Takeaway for future sweeps**: the fix-and-reverify step itself found a bug that static source/regex analysis didn't — this specific bug class (a backtick-unaware pass running before template-literal syntax is resolved) can recur at any point in the pipeline where more than one independent text-rewriting pass touches the same markup, not just the one place it was first found. Worth remembering as a concrete instance of the general principle in §7.4 below.

### 7.4 — General principle for further sweeps
Every fix in §7.1–7.3 shares a pattern: the transpiler works by pattern-matching/rewriting source text through a sequence of regex passes rather than a full AST-to-AST transform, so any JS syntax shape not explicitly anticipated by an earlier pass gets exposed to a later pass that wasn't written expecting it (here: template-literal internals being fed to the plain-identifier rewriter). Worth a systematic sweep of "one level deeper than the common case" for every transform in `php-transpiler.js` — nested template literals, tagged templates, computed member access (`obj[key]`), optional chaining mixed with array access (`a?.[0]`), destructuring with defaults, spread in JSX props.

## 8. Cross-cutting: what would have made today faster

Not an edge case, but worth recording as a process finding: the single biggest time cost today wasn't finding the bugs, it was *verifying* whether a fix had actually taken effect (caching at three different layers, admin UI hiding data depending on page template, no in-app diagnostics). A few concrete, cheap wins to consider adding to the framework itself:
- A wp-admin diagnostic page/tool that dumps `forgewp_route_id` tagging state and resolution results for every known route, in every language, on demand — turning today's multi-hour manual debugging loop into a single page load.
- A dashboard notice when a `forgewp_route_id`-tagged (or legacy-template-matched) page is not `publish` status.
- Bumping `FORGEWP_THEME_VERSION` (or similar) automatically breaking any relevant object cache keys on redeploy, if that's not already guaranteed.
