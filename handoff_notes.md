## 1. Background — what this site is

`hotelchecker24.com` is a WordPress site. Its theme was NOT built by hand in WordPress — it's generated by a compiler (a tool called "ForgeWP") from React source code, then exported as a normal WordPress theme (PHP files) and uploaded. This matters a lot for you: **you cannot fix this bug by editing files directly on the live server**, because the next time the theme is re-exported and re-uploaded, any direct edit would be overwritten. If a real fix is needed beyond what's described below, it has to happen in the *source* (a different folder on this same computer, not the live server), then get re-exported and re-uploaded. You likely won't need to do this — see Section 4.

The site is multilingual: German (default, no URL prefix, e.g. `/contact/`) and English (URL prefix `/en/`, e.g. `/en/contact-us/`). The plugin that manages this is called **Polylang**.

## 2. The bug, described precisely

On the **English** version of the live site, two things link to the wrong (German) URL instead of the correct (English) URL:

1. **The "Contact"/"Eintragen lassen" button in the site header** (top navigation bar, visible on every page). On an English page it should link to `https://hotelchecker24.com/en/contact-us/`. Instead it links to `https://hotelchecker24.com/contact/` (the German page).

2. **The "back to directory" button** on individual hotel pages and individual listicle (hotel comparison) pages. On an English hotel page it should link to the English hotels list; on an English listicle page it should link to the English listicles list. Instead, both link to the German versions: `https://hotelchecker24.com/hotels/` and `https://hotelchecker24.com/hotelvergleiche/`.

3. **Google Translate auto-translate artifact on English pages.** On `https://hotelchecker24.com/en/hotel-comparisons/` (and likely other English pages), the page's HTML was found to contain markup injected by Google/Chrome's built-in page-translate feature — extra `<p>`/`<span>` wrapper tags with attributes like `id="tw-target-text"`, `class="tw-data-text..."`, `data-placeholder="Translation"`, `aria-label="Translated text: ..."`. This is NOT something the site's own code generates — it's Chrome silently auto-translating the page and rewriting the live DOM, because the page told the browser it was in German (see Fix A below) while actually showing English text. The visible symptom to a real visitor: on some English pages, browsers may pop up a "Translate this page?" prompt, or silently mangle the text with this wrapper markup, even though the content is already in English.

**Important**: none of these three symptoms happen on the local development copy of the site (`https://hotelchecker24.local/`) — only on the live production site. That difference is itself a clue (see Section 5).

---

## 3. What has already been tried (do not redo this)

Two things were already fixed in the source code and confirmed working correctly on the local dev site:

**Fix A**: This is the fix for **symptom 3 above** (the Google Translate artifact). A hardcoded `lang="de"` attribute was found on the outer HTML wrapper of every page, even English ones, which is exactly what makes Chrome think an English page is German and silently auto-translate it. The hardcoded value was removed so the page's language attribute is set dynamically and correctly instead. This fix is NOT related to the link bug (symptoms 1–2) — it's a separate root cause that happens to produce a separate symptom. Like Fix B, **it's not confirmed whether this fix was ever uploaded to the live site** — check this the same way as described in Step 1 below, just search for a different string (see Step 1's note at the end).

**Fix B**: The actual suspected cause of the link bug. The function that resolves these links (`forgewp_resolve_page_link` in the theme's `functions.php`) calls a WordPress function called `get_pages()`, filtered by language. `get_pages()` has its own internal cache, and that cache does not know about the language filter (language filtering is added by the Polylang plugin, not by WordPress itself). The suspected effect: the *first* language that happens to run this exact query gets its result cached, and every other language's request then wrongly receives that same cached (wrong-language) result. The fix disables this specific cache for this specific query (`'cache' => false`), forcing a fresh, correct lookup every time.

**This fix was made in the compiler source and re-exported to the LOCAL site only.** It was never confirmed to be uploaded to the LIVE site. This is the single most important thing for you to check first — see Step 1 below.

## 4. Step-by-step: what to do

### Step 1 — Check whether the fix even reached the live site (do this FIRST)

This is the most likely explanation and takes 2 minutes to check.

1. Log into `https://hotelchecker24.com/wp-admin/`. (Ask the user for the login username and password — do not use any password you find written elsewhere, and do not write the password into any file you create.)
2. In the left sidebar, go to **Appearance → Theme File Editor**. (If this menu item doesn't exist or is disabled, skip to Step 1b below.)
3. On the right side, find and open **functions.php** (it may be a long file — use your browser's "find on page" / Ctrl+F).
4. Search the page (Ctrl+F in your browser) for this exact text: `forgewp_resolve_page_link`
5. You should land on a PHP function. A few lines below it, look for a line containing `get_pages_args = array(`.
6. **Check**: does that line contain the text `'cache' => false`?
   - **If YES** — the fix IS on the live site. The bug must have a different or additional cause. Skip to Step 2.
   - **If NO** — the fix was never uploaded to live. This is very likely the entire explanation. **Report this back exactly as described in Section 6** — this is not something you should try to fix yourself by editing the live file directly (see Section 1 for why). The user needs to re-export and re-upload the theme from their own computer.

**Step 1b** (only if Theme File Editor isn't available): Try to view the file another way — e.g., if the user gives you FTP/hosting file manager access, or ask the user directly whether they've re-deployed the theme to production since this fix was made. **Step 1c — also check Fix A (the Google Translate / `lang` attribute fix) the same way**: While you're in the Theme File Editor, open **header.php** (or, if you can't find it there, try **page.php** or any template file) and search for `<html`. Check the `lang="..."` attribute on that tag.
   - If it's hardcoded to `lang="de"` with no PHP code around it — Fix A was never uploaded either. Note this in your report.
   - If it looks like it's being set dynamically (e.g. contains PHP code like `<?php echo ...` or a Polylang function call rather than a plain hardcoded `"de"`) — Fix A is present on live.
   - If you can't find the `<html>` tag in the theme editor at all, note that too and move on — don't spend more than a couple minutes on this.

### Step 2 — Rule out caching plugins / CDN caching

Even if the code fix IS present on the live site, a *separate* layer of caching could still be serving old, pre-fix HTML to visitors. This is extremely common on WordPress sites.

1. Still in wp-admin, go to **Plugins → Installed Plugins**.
2. Look through the list for anything caching-related. Common names: "WP Rocket", "W3 Total Cache", "LiteSpeed Cache", "WP Super Cache", "WP Fastest Cache", "Autoptimize", "Cloudflare" (or any plugin with "cache" or "speed" or "performance" in the name).
3. **Write down the exact name of every such plugin you find, and whether it shows as Active or Inactive.**
4. If you find one that's Active: look for a "Clear Cache" / "Purge Cache" / "Empty Cache" button — it's usually either in that plugin's own settings page, or as a button/link added to the top admin toolbar (the black bar at the very top of every wp-admin page) once the plugin is active. Click it to clear the cache.
5. Also check whether the site uses Cloudflare (or any other CDN) *outside* of WordPress — you likely can't check this yourself without more access, so just note in your report if you have any reason to suspect one (e.g., a "Cloudflare" plugin was found active in step 2-3).

After clearing any cache you found in Step 2 (or immediately, if you found none):

2. Go to `https://hotelchecker24.com/en/contact-us/` and confirm this page loads correctly and is in English.
3. On that same English page, find the "Contact" button in the header (it's the pill-shaped button on the right side of the top navigation, with text that may read "Eintragen lassen" or "Get Listed").

Check symptom 3 (Google Translate artifact): on the same `https://hotelchecker24.com/en/hotel-comparisons/` page (still in your private/incognito window), right-click anywhere on the page and choose **"View Page Source"** (NOT "Inspect" — page source shows the raw HTML as delivered by the server, before any browser extensions or Chrome's own translate feature touch it). ## 5. Extra context that might help you reason about this

- Everything works correctly on the local dev copy of the site. That means the underlying *code* is very likely fine, and the issue is either (a) the fixed code never made it to the live server, or (b) something specific to the live server's environment (caching, a plugin, server configuration) that doesn't exist locally.
- The user separately confirmed, before this handoff: the English Contact page does exist, its Polylang language is correctly set to "English", and it IS linked as a translation of the German page, and it IS assigned the same page template. So a simple "the content wasn't set up right" explanation was already ruled out — which is exactly why we now suspect either a missed deployment (Step 1) or a caching layer (Step 2).
