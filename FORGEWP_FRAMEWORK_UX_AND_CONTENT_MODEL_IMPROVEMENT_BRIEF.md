# ForgeWP UX and Content Model: Remaining Work

Scope: live WordPress acceptance, component-install UX, remaining module documentation, Bing submission, and companion WordPress plugin export. Completed implementation and documentation tasks are removed from this brief; it tracks remaining work only. WooCommerce remains a separate workstream.

Preview reset tokens have no real expiry and do not replace mock login credentials. Account creation, simulated mail and preview sessions must remain distinct from WordPress accounts, inbox delivery and server-authorized sessions.

## Live WordPress acceptance

- [ ] Verify cookie/session persistence, expiry, logout failures and successful logout against an installed WordPress site, including subdirectory deployments and deployment-specific origins/caching.
- [ ] Verify default roles, approved signup metadata, capabilities and protected Pages against real WordPress users and server authorization.
- [ ] Verify registration with and without automatic login, verification-required sign-in, mail failure/retry, resend token replacement and verification-token expiry/single use.
- [ ] Assess concurrent verification-token consumption. The current transient lookup/delete rejects sequential replay but is not atomic; establish and test a stronger consume contract if concurrent single-use is required.
- [ ] Verify password-recovery delivery, frontend reset URL routing, real reset-key expiry/single use, login with the new credentials, cookies and plugin password rules.
- [ ] Verify optional JWT issuance, backend validation, expiry, rejected/unreachable restoration, logout and cross-origin protected requests against the selected JWT backend.
- [ ] Verify Auth request guards and logout nonces in real WordPress: nonce expiry/caching, allowed frontend origins/CORS, trusted proxy addresses and edge/WAF throttling under concurrent traffic and shared NATs. Transient request counters are not an atomic distributed limiter.

Generated-PHP tests use WordPress stand-ins. They verify call ordering and error paths, not real password hashing, WordPress expiry, cookie behavior or inbox delivery.

- [ ] Verify native Forms and stored-submission access with real WordPress roles, plus keyboard/narrow-admin editing and notification/receipt delivery and failure behavior. The generated implementation exists in `packages/compiler/lib/functions/forms.js`; the staging work recorded in [the forms plan](docs/archive/FORGEWP_NATIVE_FORMS_WORDPRESS_FIRST_IMPLEMENTATION_PLAN.md) remains open. Acceptance: configured capabilities govern both editing and submission access, admin controls are usable, and mail failures match the documented response contract.
- [ ] Verify Forms CSV downloads, personal-data export/erasure and scheduled retention in WordPress. CSV, privacy hooks and WP-Cron cleanup are implemented in `packages/compiler/lib/functions/forms.js`; permanent deletion is opt-in. Acceptance: exports respect permissions/field selection, privacy requests target the right records, and cleanup follows the agreed retention policy before deletion is enabled.

## Native Forms: deferred UX and capability improvements

These are future candidates from the archived forms brainstorm, not current implementation commitments. Preserve the intentional developer/client field-ownership boundary: client fields remain editable within the developer-defined slot; expanding control over developer-owned structure or validation is not an improvement item.

- [ ] Expand the native field contract: assess radio groups, multiple selections and hidden fields, plus server-enforced numeric `min`, `max` and `step`. Acceptance: supported fields work consistently in configuration, local preview, client-field editing where applicable, submission validation and stored/email output. File uploads are covered separately below.
- [ ] Improve the plugin-managed form experience: assess a useful local shortcode form preview and optional styling/adapter support for selected plugins. `WpShortcode` currently renders a placeholder locally. Define supported plugins and the limits of preview fidelity before implementation; preserve the shortcode escape hatch and native forms' plugin independence.
- [ ] Assess advanced native form capabilities: file uploads with explicit MIME/size/storage/attachment policies, optional CAPTCHA integration, multi-step flows and payment integrations. Scope these independently and define validation, failure/retry and delivery behavior before committing; they are deferred possibilities rather than requirements for every contact form.
- [ ] Server-render client-owned fields from the saved WordPress definitions. Acceptance: initial HTML reflects the active locale's saved fields (including an intentionally empty set), preserves developer-supplied markup and matches the hydrated form without duplicate fields or content swaps. Define no-JavaScript submission behavior separately; rendering alone does not provide it.

## Shared-framework findings from the Next.js fixture

These are observed in `projects/nextjs-adapter-fixture`; recording them does not enable Next.js adapter support. See `docs/nextjs-archive/nextjs-adapter-research.md` for prototype limits.

- [ ] Define source-package resolution for non-Vite consumers. `packages/react/src/hooks.ts` and `components/BlockArea.tsx` import `.js` paths whose files are TypeScript. The pinned Next webpack build fails until the fixture adds `resolve.extensionAlias`. Authors importing the public package should not have to discover this themselves. Decide whether packaging or a documented adapter configuration owns the mapping. Acceptance: a clean Next fixture resolves the public entry point with the documented setup; existing Vite consumers still pass.
- [ ] Make `WpEditable`'s preview mode safe across server/client rendering. In `packages/react/src/components/WpEditable.tsx`, Node rendering without Vite flags is non-editable, while a browser without `forgeWpHydration` becomes editable. This can make initial hydration attributes disagree. The fixture currently renders its save view until mounted, then its edit view. Define an explicit consistent preview boundary; acceptance: server and initial client output agree, local edits work, and production WordPress visitors never receive editable controls. This is a source-level finding with a fixture workaround, not a verified general fix.
- [ ] Preserve shorthand object syntax in block editor callbacks. With a declared `heading` attribute, `onChange={(heading) => setAttributes({ heading })}` reproduces a custom-edit JSX parse warning and missing `customEditJsx`. `packages/compiler/lib/blocks/index.js` rewrites matching brace text before scope-aware handling. The fixture uses `onChange={(value) => setAttributes({ heading: value })}` instead. Replace the text rewrite with syntax-aware handling; acceptance: both forms generate executable RichText callbacks and preserve callback-local bindings, with a regression test.
- [ ] Define a bundler-compatible icon provider contract. Importing `@forgewp/react` in the pinned Next fixture produces webpack dynamic-dependency warnings traced to `components/WpIcon.tsx`. This does not prove icon providers work or fail. Audit explicit provider resolution and document supported behavior; acceptance: selected providers render in production with useful missing-provider behavior and no ambiguous dynamic dependency warnings, while preserving the existing Vite path.
- [ ] Make `useWpPageLink` / `__FORGEWP_PAGELINK_*__` fallback URLs safe on WordPress subdirectory installs. In `packages/compiler/lib/markup-processor.js` (`__FORGEWP_PAGELINK_<name>_DEFAULT_<val>__`) and `packages/compiler/lib/functions/index.js` (`forgewp_resolve_page_link`), when `forgewp_resolve_route_page_id()` returns `0`, the raw fallback string (e.g. `'/legal'`) is returned directly without `home_url(...)`, whereas auth redirects in `packages/compiler/lib/generate-theme.js` and the new `forgewp_resolve_route_url()` helper wrap root-relative paths in `home_url(...)`. On a subdirectory WordPress site (e.g. `/blog`), a missing or trashed target page breaks fallback links by jumping out of `/blog`. Normalize root-relative fallback paths through `home_url(...)` while leaving external (`https://`, `mailto:`) and `#fragment` fallbacks verbatim; acceptance: PHP runtime tests cover root and subdirectory fallback resolution plus external/hash passthrough without breaking existing `use-wp-page-link.test.js` contracts.
- [ ] Clarify and reconcile auto-created template Pages (`routing.js`) with `cms/mock-data.(ts|json)` `page` records. `packages/compiler/lib/functions/routing.js` (`forgewp_auto_create_pages_and_menus`) creates empty WordPress `page` stubs for compiled templates on theme activation, while `packages/compiler/lib/functions/seed-mock-data.js` seeds `mock-data` `page` records separately only when `config.seed.mockData` opts in. Authors declaring `page` entries in `cms/mock-data.ts` alongside compiled page templates (`src/app/pages/*.tsx` or Next `src/app/**/page.tsx`) can be unsure which source owns initial WordPress titles/content or whether they collide. Document the ownership boundary clearly and evaluate coordinating `seed.mockData` `page` upserts with `forgewp_route_id` / `_wp_page_template`; acceptance: documented ownership rules and a PHP seeding test confirming a seeded `page` preserves its assigned template and `forgewp_route_id` without creating duplicate pages.
- [ ] Route `validateCriticalFiles()` preflight through the active framework adapter's `getCriticalFiles()` hook. `packages/compiler/lib/validate.js` currently requires Vite/React-specific files (`index.html`, `src/main.tsx`, `src/app/routes.tsx`) and runs in `export-theme.js` before `loadConfig()`, even though `ForgeWPFrameworkAdapter` already defines `getCriticalFiles?(themeRoot)`. Non-Vite adapters (such as Next.js App Router) do not use `index.html`, `src/main.tsx`, or `src/app/routes.tsx`. Load config/adapter before preflight or let adapters supply required entry files; acceptance: React/HTML preflight errors stay unchanged, while a custom adapter validates only its own declared critical files.
- [ ] Ensure `front-page.php` establishes WordPress post loop context before including `forgewp-static/content.html` when rendering a static front page. In `packages/compiler/lib/php-builders.js`, `buildGeneratedPageTemplateContentPhp()` wraps custom page templates (`page-*.php`) in `if (have_posts()) { while (have_posts()) { the_post(); ... } }`, so `<BlockArea />` (`<?php the_content(); ?>`) renders saved Gutenberg blocks on custom pages. By contrast, `buildIndexPhp()` (`front-page.php`) includes `forgewp-static/content.html` directly inside `if (is_front_page() && file_exists($markup_file))` without calling `the_post()` unless the front page switches to `template-forgewp-builder.php`. When an author places `<BlockArea />` on the home page with a static front page assigned, `the_content()` runs without post data initialized. Initialize `the_post()` (when `is_front_page() && have_posts()` with a static page) or document the boundary; acceptance: a PHP/live-WordPress test verifies `<BlockArea />` on a static front page renders saved Gutenberg blocks without requiring `template-forgewp-builder.php` and without breaking Polylang or posts-index front pages.

## Component installation UX

- [ ] Define and implement an inspectable, recoverable component-install plan. `packages/compiler/lib/add-component.js` currently invokes upstream installation, writes local overrides, then processes Tailwind plugins; the local metadata contract is not a general dependency installer. A later failure can leave a partially changed project. Acceptance: a dry run identifies sources/files/dependencies, local registry dependency fields have an explicit supported contract, and failure tests establish rollback or precise recovery instructions. The [registry review](docs/archive/component-registry-ux-review.md) records the proposal; this item does not claim transactional installs already exist.
- [ ] Make upstream overwrite behavior explicit and test it independently from local overrides. `add-component.js` protects existing ForgeWP-local files unless `--overwrite` is supplied, but delegates upstream components to `shadcn add --yes`. Acceptance: existing customized upstream files are tested against the selected CLI, help accurately states flag scope, and update/replacement behavior is documented without implying that local protection covers upstream installs.
